설치형(온프레미스) 치과 EMR을 웹·데스크톱 애플리케이션으로 옮기는 프로젝트였습니다. 업무 상태, 접근 권한, 진료비 산정처럼 처음 설계가 정확해야 하는 기능들을 정의하고 구현했습니다.

## 1. 업무 상태를 상태 머신으로 정의

- **상황**: 치과 환자는 예약부터 진료 완료까지 7~8단계를 거치고, 일부 단계는 건너뛸 수 있습니다. 데스크와 진료실은 같은 환자의 진행 상태를 실시간으로 봐야 했습니다.
- **판단**: 조건문으로 상태 전이를 직접 제어하는 방식과 유한 상태 머신을 선언적으로 정의하는 방식을 비교했습니다. 복잡한 전이 조건을 한곳에서 관리하고, 허용되지 않은 전이를 코드 수준에서 막기 위해 XState 도입을 제안했습니다.
- **구현**: 치과 환자의 진료 흐름을 관리하는 상태 머신(D-CFM)을 설계하고, WebSocket으로 데스크와 진료실 화면의 상태를 실시간 동기화했습니다.

```
예약 → 접수 → 대기 → 준비 → 진료중 → 상담·안내(생략 가능) → 수납대기 → 완료
```

## 2. 로그인 인증과 EMR 실행 권한을 분리

- **상황**: 의사, 치위생사, 코디네이터 등 직원 역할에 따라 쓸 수 있는 기능이 다릅니다. 병원의 구독·결제 상태에 따라 EMR 실행 자체도 막아야 했습니다.
- **판단**: 사용자가 누구인지 확인하는 인증과 EMR을 실행할 수 있는 권한은 기준이 다르다고 봤습니다. 직원 역할이 바뀌거나 병원 구독이 끝날 수 있기 때문입니다. 그래서 Access·Refresh 토큰과 별도로, EMR 실행 권한을 확인하는 Execute 토큰을 두는 3계층 인증(ARE)을 설계했습니다.
- **구현**: NestJS 미들웨어에서 세 토큰의 유효성과 서로 간 정합성을 검증합니다. 프론트엔드는 공통 훅으로 실행 권한을 같은 방식으로 확인합니다.

## 3. 진료비 산정을 화면부터 DB까지

건강보험 수가코드와 보험 체계를 반영해 최종 진료비를 계산하는 기능을 맡았습니다. 화면 구현, 진료비 계산 로직, DB 저장까지 전 과정을 혼자 했고, 건강보험 청구 심사 신청 일정을 처음 계획보다 **2주** 앞당겼습니다.

## 4. 자문 치위생사의 피드백 경로 단축

덴티움이 운영하는 치위생사 자문단 '브레인스펙'(10~15명)은 EMR을 직접 써 보며 개선 의견을 줬습니다. EMR 안에서 바로 메모를 남기고, 남긴 의견을 실시간으로 볼 수 있는 기능을 Apollo Subscriptions로 만들었습니다. 자문단은 다른 화면으로 옮겨 가지 않고 쓰던 자리에서 의견을 남길 수 있게 됐습니다.
